# 검토보고서 색인 데이터 계약 (review 1.0.0)

상임위원회 전문위원실이 만드는 「예산안·기금운용계획안 검토보고서」를 색인한다. 부처가 낸 사업설명자료(`schema.md`)와 다른 문서이며, DB도 따로 둔다.

## 검증 범위

- **검증한 자료**: 2027년도 과학기술정보통신부 소관 예산안·기금운용계획안 및 BTL 한도액안 검토보고서(과학기술정보방송통신위원회, 과방위, 2026. 11.). HWP 607쪽을 kordoc 4.22.13으로 변환한 Markdown(약 45,500줄)에서 소관과 18곳, 사업(주제 포함) 60개, 쟁점 152개가 목차와 일치했다.
- **다른 상임위 보고서**: 같은 편집 관례(목차, Ⅰ 개관, Ⅱ 검토의견, 소관과 → 【회계】 → 사업(코드) → 가)·나)·다) 쟁점)를 따를 것으로 보고 같은 어댑터로 시도할 수 있게 했다. **실물로 검증하지 않았다.** 처음 쓸 때 `build` 출력의 `toc_check`(오류·경고)와 `REVIEW_CATALOG.md`를 반드시 확인한다. 어긋나면 게시하지 않고 오류를 낸다.

## 저장과 정체성

`.budget-index/review-config.json`: ministry/ministry_id, fiscal_year, committee(id, name, short), edition(id, stage=`committee_review`, published_at), adapter=`committee-review-report`, markdown_glob(보고서 1개와 일치), 선택값 expected_units·patterns·account_names.

`.budget-index/review.sqlite`: 한 판본의 사업·쟁점·본문 블록을 담는 재생성 가능 캐시. 임시 DB를 만든 뒤 단일 파일로 교체한다. 목차 대조 오류가 있으면 게시하지 않고 기존 DB를 보존한다. 사업설명자료 색인(`budget.sqlite`)은 만들지도 바꾸지도 않는다.

`.budget-index/REVIEW_CATALOG.md`: 소관과·회계·사업·쟁점 제목·원문 행 목록(사람이 `toc_check`와 함께 훑어보는 용도).

`id`: `{연도}-{부처}-review-u{순번}`(사업·주제) 또는 `…-c{순번}`(개관 구간). `uid`: `id@판본ID@원문해시앞16자리`.

## 레코드

- `kind=unit`: 검토의견의 사업 1개(코드 있음) 또는 총괄 주제(코드 없음). 필드: dept(소관과), account(회계·기금 원문 명칭), account_source(`body`|`toc`), title, code, codes, header(원문 머리글), issues(label, title, start_line, end_line), start_line/end_line, source, source_sha256.
- `kind=context`: Ⅰ 개관의 총괄·회계별 구간(사업 단위가 아니다).
- 블록: 문단 또는 완결된 표. 필드: section(`사업 머리글` | `검토요지` | `가) 제목`…), issue_label, is_table, caption(`<…>` 표 제목), unit_raw(`(단위: …)`의 원문), text.
- 하나의 사업에 쟁점이 여러 개다. `가) 사업 및 예산안 개요`는 설명이고 `나)` 이하가 검토 쟁점이다. `검토요지`는 쟁점 앞의 `◦ …할 필요가 있음` 문장들이다.
- 총괄 주제 중 코드 없는 것은 사업설명자료와 연결되지 않는다.

## 사업설명자료와의 연결

`search`·`show`는 `budget.sqlite`를 읽기 전용으로 찾아 `program_link`를 붙인다. 합치지 않고 연결만 한다.

**코드만으로 연결하지 않는다.** 사업 코드는 회계가 다르면 중복될 수 있다. 실제 사업설명자료(2027년 과기정통부 정부안)에서 서로 다른 회계의 사업이 같은 코드를 쓰는 경우가 여러 건 확인됐다(수치는 `windows/VALIDATION.md`). 예를 들어 가상의 두 사업 「GPU 임차 지원」(일반회계)과 「지역 AI 실증」(지역균형발전특별회계)이 모두 `1111-111`을 쓰면, 코드만으로는 어느 쪽인지 알 수 없다. 그래서 같은 코드의 후보 중 **제목이 맞는 사업만** 연결한다(`match`: `title_exact` | `title_contains`(한 머리글에 여러 사업이 묶인 경우 포함) | `title_similar`(유사도 0.85 이상)). 코드만 같은 다른 사업은 `same_code_other_programs`에 따로 보이고 연결 대상이 아니다. 제목이 맞는 후보가 없으면 `linked: false`와 `code_only_candidates`를 낸다. `account_agrees`는 회계 표기가 같은지 보여 주는 참고값이다.

연결되지 않으면 이유를 적는다: 색인 없음, 회계연도 다름, 같은 코드 없음(세입 항목이거나 다른 판본), 제목이 맞지 않음, 코드 없는 항목(총괄 주제). 같은 코드의 다른 연도를 합치지 않는다. 두 문서의 판본·시점이 다르면 제목이나 코드가 달라질 수 있으므로, 처음 쓸 때 연결되지 않은 항목의 이유를 확인한다.

## 검증하는 것과 하지 않는 것

`build`가 목차와 본문의 소관과·사업을 대조한다(불일치 시 실패). 회계 구분과 쟁점 제목은 경고로 보고한다(본문에 【회계】 머리글이 빠진 경우 목차 기준으로 채우고 `account_source: toc`로 표시). `verify`는 원문 해시, 행 범위, 쟁점·블록 경계를 검사한다.

**쟁점 내용의 의미, 표의 금액·단위·열 해석은 자동으로 증명하지 않는다.** 금액은 `show`로 전체 표(제목·`(단위: …)`·열 머리글·`자료:`)를 읽고 연도·단위를 확인한다. 보고서는 `본예산(A)`·`추경`·`예산안(B)`을 섞어 쓰므로 열 제목을 확인한다.
